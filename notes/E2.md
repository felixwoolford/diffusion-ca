# E2 — Write-size matrix (SPEC §6)

**Question:** {1024, 512, 256} × {t2i, edit_self, edit_neighborhood}:
post-quantize 32-art fidelity, style adherence, latency.
SPEC §4 expectation: 512 ≥ 1024 quality-per-second; **256 capped at 16-art**
(the model "really paints 16×16 and interpolates").

**Date:** 2026-10-17. **Server:** 127.0.0.1:8189 (4080/16GB),
`qwen_image_2.1_int8_convrot.safetensors`. Turbo 8-step untouched.
**Seed:** 42 for all 9 cells. Script: `experiments/e2_write_size.py`
(re-analyze with `--no-generate`); raw `images_out/e2/e2_results.json`.

**Test tile** (32×32, dev palette; [`test_tile_256.png`](test_tile_256.png)):
- TR quadrant flat green, BL quadrant flat blue (16px features)
- TL and BR quadrants: 2×2 checker of 8×8 white/black squares (8px features)

**Prompts:** canned per arm (t2i = full description; edit arms = "keep the
tile exactly as it is" + description), all ≤500 chars. No vision rule model
involved — E2 isolates the diffusion path; rule quality is E3.

## Findings

1. **The "256 caps at 16-art" expectation (SPEC §4) is contradicted — flag.**
   With a reference image, both edit arms reproduced the 8px (half-latent at
   256²: latent is 16×16) checkerboard **exactly** (exact = 1.0, all 8
   squares correct). The VAE/edit path can write sub-latent geometric detail;
   the 16-art "cap" is not a hard VAE limit. It does apply to the
   **text-only** arm: t2i at 256 degraded (0.73, TR quadrant color wrong,
   checker fills impure) — with no reference, the model's own 16×16 latent
   painting shows through. See [`t2i_256_preview.png`](t2i_256_preview.png) /
   [`t2i_256_quant.png`](t2i_256_quant.png).
2. **Edit arms are a near-perfect copy channel** for this geometric tile at
   all sizes (7/9 cells exact). Two failures: t2i 1024 (0.93,
   [`t2i_1024_quant.png`](t2i_1024_quant.png)) and edit_neigh 512 (0.75 — the
   TR quadrant came out with the wrong dominant color,
   [`edit_neighborhood_512_preview.png`](edit_neighborhood_512_preview.png)).
3. **Latency** (4080/int8, turbo): 256 ≈ 2.4–2.8 s; 512 ≈ 2.5 s
   (t2i/self), 6.9 s (neigh); 1024 ≈ 5.0 / 9.0 / 28.0 s. The five-reference
   `edit_neighborhood` arm costs 2–4× the single/no-reference arms at the
   same size.
4. **Quality-per-second: 512 is the sweet spot** for this tile — every arm
   is at or near perfect at 2.5–7 s; 1024 buys no measurable fidelity here
   (t2i 1024 was actually the *worst* non-256 cell) at 2–10× the cost.
5. **Engineering:** node `13` (ResolutionSelector) has `megapixels` min 0.1
   (= 320 px at 1:1) — t2i below that must go through node `488`
   (EmptyLatentImage) directly. The engine now falls back automatically
   (`ArmSpec.size_node_small`); verified by `t2i_256`.

## Caveats

- Single seed, one geometric (not naturalistic) tile: exact-match 1.0 says
  the *channel* is lossless for this content; harder motifs will degrade.
- "Keep exactly" is a degenerate rule prompt (E2 isolates diffusion; the
  real rule's prompt quality is E3's question).
- **Style adherence is not measurable in the metrics** — Felix: review the
  committed previews (`*_preview.png`) for style/texture quality.
