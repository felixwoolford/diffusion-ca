# E3 — Read-size matrix (SPEC §6)

**Question:** at neighborhood-render read sizes {256, 512, 1024}, does the
rule model correctly identify the tiles and describe neighbor relations?
Fixed probe questions about known 5-tile composites.

**Setup** (kept minimal — the multimodal deployment is slower and has a
smaller context; Felix 2026-10-17):

- Rule model: `qwen3.8-27b-ud-q6-k-xl-multimodal` via the llama.cpp router
  at `127.0.0.1:8080` (loaded by Felix 2026-10-17 ~18:30 UTC).
- Composites are exactly what the pipeline renders: `render_cross` with
  labels, 32×32 art tiles from the dev64 palette, flat unambiguous colors.
  - **main**: C=red, N=blue, E=yellow, S=green, W=quadrant split
    (red / pale pink `#f0d1d6`)
  - **alt**: C=green, N=yellow, E=red, S=blue, W=horizontal split
    (pale pink / green)
- 7 fixed questions per call: 4 color identifications, 1 sub-tile structure
  (quadrants / halves), 1 position lookup ("which tile is X, by label"),
  1 same-color relation. Numbered one-line answers, temperature 0.1,
  thinking disabled (finding 4).
- Calls: main @ 256 / 512 / 1024 + alt @ 512 (fluke check) = 4 calls,
  28 questions. Script: `experiments/e3_read_size.py`.

**Result: 28/28 correct.**

| call | composite | read size | correct | latency | prompt tokens |
|---|---|---|---|---|---|
| main_256 | main | 256 | 7/7 | 13.6 s (first call, warm-up) | 844 |
| main_512 | main | 512 | 7/7 | 1.9 s | 2572 |
| main_1024 | main | 1024 | 7/7 | 3.6 s | 4364 |
| alt_512 | alt | 512 | 7/7 | 1.9 s | 2577 |

Example answers (main_512): `1. Red  2. Blue  3. Yellow  4. Green  5. Red,
pink  6. E  7. No` — all matching ground truth.

**Findings**

1. **The rule reads the labeled cross composite perfectly at all three
   read sizes** — color identity, position lookup via the drawn-in labels,
   same-color relations, and sub-tile structure (16-art-px quadrants and
   half-splits) are all correct. No measurable accuracy difference between
   256 / 512 / 1024.
2. **Content-class caveat:** probe features are ≥ 16 art-px (solid fills,
   quadrants, halves). Finer features (8 art-px, e.g. checkerboards) are
   untested; E6 (real evolving content) will exercise them.
3. **read_size 1024 is capped server-side.** A 3072² composite should cost
   9216 visual tokens, but prompt_tokens show 4364 − 268 (text) = **4096
   visual tokens exactly (64×64)** — the deployment caps images at
   2048×2048, so "read_size 1024" is actually served at ~683 px per tile.
   That is 1.7× the tokens of 512 for < 2× the linear resolution, with zero
   accuracy gain here. → no reason to use read_size 1024 on this
   deployment.
4. **Thinking-model gotcha (engine fixed).** The multimodal deployment is a
   *thinking* model: without `chat_template_kwargs: {"enable_thinking":
   false}` the whole token budget goes to `reasoning_content` and the
   visible content comes back empty (first E3 run: 4/4 calls empty,
   finish_reason=length). The engine's `llamacpp` backend now disables
   thinking (regression test in `tests/test_rule.py`). `pi_agent` is
   unaffected (pi handles thinking natively).
5. The model describes palette colors in natural language ("Red, pink" for
   red + `#f0d1d6`) — the dev64 "white" is a pale pink; expected, and the
   CA rule's prompt carries the pixel-art frame, not probe questions.

**Conclusion:** default `read_size` 512 is validated (28/28). 256 also
passes for features ≥ 16 art-px and costs a third of the tokens. 1024 is
not worth it on this deployment (served at ~683 px/tile, no accuracy
gain). No config change needed.

**Evidence:** composite previews (256 px) in `notes/e3/`; raw responses,
per-question scores and token usage in `images_out/e3/e3_results.json`
(gitignored).
